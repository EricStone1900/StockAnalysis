# ADR-020：执行一致性与可复现交付门禁

- 日期：2026-09-05
- 状态：ACCEPTED（用户授权架构审查整改）
- 范围：阶段01、05、07、10、12；不授权生产券商下单。

## 决策

1. 执行服务必须通过可信授权端口验证批准、风险、持仓版本、完整指令Hash、有效期和DISPATCHING预算；没有真实授权适配器时失败关闭。请求中的ID、布尔字段和自算Hash不能作为授权证明。
2. 批次、全部Intent、业务幂等记录和Outbox在同一个数据库连接的事务中提交。消费者的Inbox和业务写入同事务；跨服务继续使用Saga，不引入分布式数据库事务。
3. 工作流在执行接受结果未知或接受后失败时不得释放预算。只有权威执行服务明确确认未接受时才能释放；UNKNOWN保留占用并进入查询/人工恢复。
4. portfolio-risk拥有资源占用，治理只拥有批次次数预算。资源预留绑定portfolioId、ledgerVersion、proposalVersion、指令Hash和风险版本；原子校验可用现金、费用缓冲和可卖数量。在途委托、部分成交和UNKNOWN继续占用，禁止按超时自动释放。
5. 首版同一组合仅允许一个未结束批次。买入不得提前使用未确认卖出所得；执行计划必须验证中间现金和风险暴露。批次次数上限不替代资源校验。
6. 当前机器契约根为`packages/contracts/`。旧文档的`contracts/`路径为目标结构，不是第二套事实源。Schema生成产物必须通过漂移检查。
7. 验收分为UNIT、FAKE_INTEGRATION、REAL_E2E、RELEASE四类，分别绑定提交、配置、入口、版本、日志和签署。历史人工确认保留，但不推导为当前提交的发布PASS。
8. Fake Worker只能显式用于demo/test。真实模式不得悄悄使用Fake。Mac与Ubuntu使用同一业务冒烟门禁，平台差异单独记录。

## 交付顺序

保留各服务S0～S6。跨阶段允许按下列依赖形成最小验证闭环，替代“全部增强能力完成后才联调”的总串行约束：

- M1：阶段02/03已验收的真实数据和分析，通过阶段07只读页面展示。
- M2：阶段05的批准、风控、预算、执行、成交和持仓在隔离环境形成REAL_E2E。
- M3：阶段10接入已独立验收服务，验证真实Temporal恢复；阶段12的Paper能力可提前用于M2/M3验证。
- 自动研究（04）、全部市场情报（06）、学习（11）不是M1/M2的硬依赖。生产Agent和自动交易仍遵守各自权限、数据与发布门禁。

## 验收与回滚

强制用例：伪造授权、旧批准、并发资源竞争、事务中途失败、提交后重启、不同载荷重复幂等键、接受结果丢失、部分成交后异常、Fake运行模式误配。权限、资金、幂等或恢复失败判FAIL。

默认关闭自动交易。整改只添加兼容迁移，不删除历史账本；回滚应用前保留数据库、Outbox和UNKNOWN批次，禁止回滚后重发已有委托。各阶段验收必须说明哪些用例已经执行，不能以本ADR代替运行证据。
